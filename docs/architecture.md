# 架构设计文档

本文档说明 Music（P2P 流媒体音乐播放器）的整体架构、服务器分层，以及本地开发阶段的推进计划。

## 1. 设计核心：两类"服务器"必须分开

P2P 播放器里的"服务器"其实是两个职责完全不同的东西，从第一天就要分清，否则后期会被迫重构。

| 组件 | 职责 | 能否最后做 |
|------|------|-----------|
| **账号服务器 (Account)** | 管"你是谁"：注册、登录、token 鉴权 | ✅ 可以最后做 |
| **Tracker / 信令服务器 (Signaling)** | 管"节点在哪"：节点上线注册、查询谁有哪些分片、撮合两个节点建立连接（NAT 穿透） | ⚠️ 不能最后做，是 P2P 地基 |

**结论**：账号登录可以拖到最后；但"节点如何找到彼此"必须早想清楚，哪怕本地开发时用最简实现。

## 2. 三条铁律（现在就定，省后面痛苦）

1. **节点身份 ≠ 用户身份**
   每个客户端启动时生成 `peer_id`（随机 / 设备指纹）。P2P 网络只认 `peer_id`；用户账号是后来"绑定"到 peer 上的一层。两者解耦，账号系统才能真正最后做。

2. **网络层依赖抽象接口**
   例如 `PeerDiscovery.findPeers(resourceHash)`。底层今天是内存实现、明天是远程 Tracker，播放器上层代码不用改。

3. **资源用内容哈希寻址**
   曲目切片后对每个分片算 hash，用哈希定位资源。这是 P2P 去重、多源下载的基础，且与账号无关，第一天就要这么设计。

## 4. 本地开发阶段计划

把地基留出来，但每个阶段用最简实现，不提前造复杂度。

### 阶段一 ✅ 已完成 —— 不做账号，做极简 Tracker
- **账号**：无登录 UI，节点只认随机生成的 `peer_id`。
- **ChunkStore**（`chunk.rs`）：256 KiB 切片、SHA-256 内容寻址、去重、哈希校验、重组。
- **Tracker**：进程内 `InMemoryTracker`，内存维护「节点表 + 分片索引」。
- **前后端打通**：导入音频 → Rust 切片/哈希/入库 → 重组 → 播放，字节级无损。
- **约束**：网络层通过 `PeerDiscovery` 抽象接口发现节点，不硬编码 IP。

### 阶段二 ✅ 已完成 —— 跨进程真 P2P
- **独立 Tracker 服务**（`tracker.rs`，`music --tracker`）：TCP + 行分隔 JSON 协议，
  提供 register / announce / find / publish / list / unregister。
- **RemoteTracker**（`peer.rs`）：实现同一个 `PeerDiscovery` trait，短连接请求 Tracker
  —— 印证铁律之二，上层代码零改动即从内存实现切到远程。
- **分片直传**（`transfer.rs`）：每个客户端后台开分片服务，节点间用 TCP 二进制协议
  按哈希直传分片；下载时逐分片 `find_peers → fetch_chunk → 校验入库 → announce`。
- **验证**：本机开 Tracker + 两个客户端，一端发布、另一端从共享曲库下载并播放，
  分片真实跨进程传输；下载后本节点也成为该分片的源（多源分发）。
- **本阶段边界**：仅本机/局域网；NAT 穿透留待后续。

### 阶段二·流式 ✅ 已完成 —— 边下边播
- **自定义 `stream://` 协议**（`stream.rs`）：`<audio>` 按 HTTP Range 请求媒体字节区间，
  每个区间背后按需拉取所需分片（缺片才 `find_peers → fetch_chunk → 校验入库`）。
  单次只返回有界窗口（1 MiB），保证分片是"边播边拉"而非一次拉完。
- **ChunkStore.read_range**：跨分片切出任意字节区间；`chunks_for_range` 计算区间覆盖的分片下标。
- **优势**：浏览器原生管缓冲/解码/seek，全格式通吃（MP3/FLAC/AAC…），播放条的"已缓冲"
  底层自动反映真实渐进缓冲 —— 这正是快播式流媒体的本质。
- **前端**：网络视图「播放」= 流式即点即播（`prepare_stream` 拿 URL 交给 `<audio>`）；
  「下载」保留为完整收藏到本地。
- **本阶段边界**：按需串行拉取（未做预取/多源并行同区间调度）。

### 阶段二·多源加速 ✅ 已完成
- **并行分片拉取**（`transfer.rs` 的 `fetch_chunks_parallel`）：缺失的分片由固定大小
  线程池（默认并发 4）从各自持有者**同时**拉取，而非逐片串行等待。
  用 `std::thread::scope` + 共享任务队列实现，无新依赖。
- **两处调用点统一复用**：`stream.rs` 的 `ensure_range_available`（流式按需拉）
  和 `lib.rs` 的 `download_track`（完整下载）。
- **批量 announce**：拉完一批后一次性向 Tracker 宣告，而非每片一次往返。
- **完整性不变**：`store.put` 内部仍校验 SHA-256；`ChunkStore` 本就线程安全；
  分片按哈希寻址，拉取顺序不影响重组。
- **验证**：单测 `parallel_fetch_is_actually_concurrent` 给每片注入 120ms 延迟，
  4 片串行需 480ms，实测约 130ms（≈1 次往返，约 3.7× 加速）。
- **本阶段边界**：未做预取、未做单分片多源竞速（避免带宽浪费）。

### 阶段二·分片持久化 ✅ 已完成
- **磁盘缓存**（`chunk.rs` 的 `ChunkStore::open`）：分片按内容哈希存为文件
  `<app_data_dir>/chunks/<hash前2位>/<完整hash>`，两级目录避免单目录堆积。
  内容寻址天然适合文件系统 —— 文件名即哈希，无需额外索引文件。
- **内存只留索引**：`HashSet<String>` 记录持有哪些 hash，分片内容不驻留内存。
  启动时扫目录重建索引，内存占用不再随缓存增长。
- **原子写**：先写 `.tmp` 再 `rename`，避免崩溃留下半截文件；
  扫描只认合法 64 位 hex 文件名，残留 `.tmp` 自动忽略。
- **双模式**：`new()` 纯内存（测试用），`open(dir)` 磁盘持久化（生产用）。
  对外方法签名不变，所有调用方零改动 —— 已有测试成为天然回归网。
- **重启后继续供源**：启动时把恢复的分片一并向 Tracker 宣告。
- **验证**：单测覆盖跨重开恢复、`.tmp` 忽略、磁盘模式下的哈希校验；
  真机验证 —— 导入 3 片 → 杀进程 → 重启读到 `3 chunks restored`
  → curl 跨分片 Range 返回字节完全一致。
- **本阶段边界**：未做缓存淘汰 / 容量上限（需要 LRU + 用户可配）；
  曲库列表未持久化（分片在，但重启后曲目列表清空）。

### 阶段二·曲库持久化 + 缓存淘汰 ✅ 已完成
这两件事天然配对：曲库定义了"我的收藏"，淘汰才知道哪些分片轻、哪些重。

- **曲库持久化**（`library.rs`）：曲目清单（manifest + 标题/艺术家/mime）存成
  `<app_data_dir>/library.json`，原子写（`.tmp` → rename）。启动时恢复，
  前端为每首调 `prepare_stream` 拿 URL —— 分片都在本地，**离线秒播**
  （`ensure_range_available` 在分片齐全时直接返回，不碰网络）。
  JSON 损坏时备份为 `.bak` 并以空库启动，不静默丢用户数据。
- **带保护的 LRU 淘汰**（`chunk.rs` 的 `evict_if_needed`）：
  - **访问时间用文件 mtime** —— `get()` 成功后刷新 mtime。零额外状态文件、
    天然崩溃安全。代价是每次读多一次 `set_times`，远小于网络 IO。
  - **保护集合** = 曲库所有曲目的分片并集（`Library::protected_hashes`）。
    自己导入/下载收藏的永不被删；只回收流式播放顺带缓存的"过路分片"。
  - 默认上限 2 GiB（`DEFAULT_CACHE_LIMIT`），超限后淘汰到 80% 水位，
    避免卡在上限反复触发。导入/下载/移除后与启动时各检查一次。
- **验证**：单测覆盖 LRU 顺序、保护生效、未超限不动手；真机端到端 ——
  1.9 MB 缓存 + 0.5 MB 上限 → 淘汰 8 个过路分片释放 1.6 MB，
  降到 300 KB（正好剩受保护的曲库分片），曲库曲目仍能完整重组，
  library.json 重开后恢复。
- **本阶段边界**：上限不可在 UI 调整；淘汰后未向 Tracker 撤销宣告
  （Tracker 无此协议；对方拉取失败会自然改用其他源）。

### 阶段三 ✅ 已完成 —— 账号系统

**铁律之一的验证结果**：`PeerInfo` 里从头到尾没有用户字段，所以账号真的是
"加一层"而不是重构 —— `peer.rs` / `transfer.rs` **零改动**。当初的解耦成立。

- **账号存储**（`accounts.rs`，Tracker 侧）：
  - 密码用**每用户独立随机盐 + PBKDF2-HMAC-SHA256（10 万轮）**派生存储。
    HMAC 由已有的 sha2 手写实现，通过 RFC 4231 测试向量验证正确性。
  - 账号持久化到 `tracker_accounts.json`（原子写）；**token 只在内存**
    —— Tracker 重启后失效，不会有长期 token 留在磁盘上。
  - token 有效期 7 天；`verify` 顺带清理过期条目。
  - 常量时间比较密码哈希；登录失败不区分"用户不存在"与"密码错误"，
    避免用户名枚举。
- **鉴权范围**：只有**发布**需要登录。浏览共享曲库 / 下载 / 流式播放
  **保持开放** —— 维持"人越多越流畅"的 P2P 性质。
- **协议扩展**：`register_account` / `login` / `logout` / `whoami`；
  `publish` 新增 token 字段，`SharedTrack` 新增 `publisher` 字段
  （共享曲库能看到谁发布的）。
- **客户端会话**：token 持久化到 `session.json`，重启免登录。
  `current_user` 启动时向 Tracker 校验；token 失效则清本地会话，
  但 Tracker 不可达时**保留**会话，不因网络抖动把人登出。
  **登出不影响 P2P 传输** —— peer_id 与分片供源照常。
- **验证**：10 个单测（含 HMAC 已知向量、错误密码、重复注册、token 过期/吊销、
  账号跨重启）；真机端到端 13 项全通 —— 无 token/伪造 token 发布被拒、
  带 token 发布成功且 publisher 正确、登出后已吊销 token 被拒、
  Tracker 重启后账号仍可登录（磁盘上只有盐和派生哈希，无明文密码）。
- **本阶段边界（诚实标注）**：
  - Tracker 协议是**明文 TCP**，密码传输未加密。仅适用于本机/局域网学习场景，
    公网部署必须套 TLS。
  - PBKDF2 不如 Argon2id 抗 GPU 并行破解（选它是为了零新依赖）。
  - 随机数用时间/PID/ASLR 熵源派生，非 OS CSPRNG。生产应换 `getrandom`。
  - 未做密码找回、邮箱验证、用户资料页。

## 5. 关键抽象接口（示意）

```
// 节点发现 —— 底层实现可替换（内存 / 远程 Tracker）
interface PeerDiscovery {
  register(peerId, addr, ownedChunks)      // 上线注册自己
  findPeers(resourceHash): Peer[]          // 找谁有这个资源
  unregister(peerId)                       // 下线
}

// 资源寻址 —— 内容哈希
type ResourceHash = string                 // 分片内容的 hash
interface ChunkStore {
  has(hash): boolean
  get(hash): bytes
  put(hash, bytes)
}
```

## 6. 合规

仅用于 P2P 流媒体传输技术的学习与研究。Tracker 与客户端不得用于分发未授权的版权音乐资源。
